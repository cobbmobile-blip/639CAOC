1. WHAT THE SITE IS
--------------------------------------------------------------------------------
A website for the 639th virtual Combined Air Operations Center (CAOC) that runs
DCS World campaigns for many independent squadrons/groups. CAOC staff build the
planning products (Commander's Intent, AOD, JIPTL, TDP, ATO, ACO, SPINS, Comm
Plan, BDA). Participating groups sign in to an "Op Status" portal to pull the
released products. Products apply to a WHOLE GROUP, not to individual flights.

Current state: a working clickable PROTOTYPE -- static HTML/CSS/JS, no backend.
Data lives in the browser (localStorage) and logins are a demo gate only.
Everything for DKS goes out through ONE PUBLISH button on the CAOC
Dashboard; there are no per-page "Send to DKS" buttons (the PRCC's rescue
buttons excepted). Until the integration is built, PUBLISH queues the
events in the prototype's DKS outbox; their data is defined in 4.6.

Run it: serve the repo root with any static server, e.g.
    python -m http.server 8765
then open http://localhost:8765/login.html

Demo logins (prototype only):
  Staff:  ATLAS (CFC), OVERLORD (CFACC), SPARTAN, CHALICE, WIZARD, DARKSTAR
          password: aoc-demo
  Groups: viper, hornet, eagle, hawg, knights, tomcat, harrier, mistral,
          thunder, keepers, ridge, support      access code: unit-demo
          ("viper" = Viper Ops Group = the JFACC group for OP IRON TRIDENT)

2. WHO DOES WHAT (ROLES)
--------------------------------------------------------------------------------
  CFC         Manages the CAOC. Decides on campaign proposals (accept /
              return / decline). Can assist the CFACC (approve/publish).
  CFACC       Makes sure every deliverable is built and approved. Approves and
              publishes products. Does NOT manage the campaign.
  CAOC staff  Build products and submit them for CFACC review.
  Group JFACC Elected by the group that sponsors/submits a campaign. Manages
  / LNO       the campaign and is the CAOC's single point of contact.
              Requests ATO lines for the campaign.
  Groups      Registered DCS squadrons/groups (name, airframes, liaison...).
              Pull products from Op Status; commit to ATO lines via Discord.

Product workflow: Draft -> Submit for review -> Approved (CFACC/CFC) ->
Published to groups. Publishing freezes a versioned snapshot (v1, v2...);
groups always get the released version, never a draft. Any edit after
approval goes back to Draft and needs re-approval.

--------------------------------------------------------------------------------
3. THE CAMPAIGN CYCLE, END TO END
--------------------------------------------------------------------------------
The CAOC only BUILDS PRODUCTS. It does not play in the campaign, does not edit
the host's .miz, and does not run readiness, the mass brief or the mission --
those are the host unit's alone. Deadlines (days before T-0 = first mission)
are on the CAOC Dashboard (index.html) and are editable per campaign.

  1. Proposal (T-42). A group submits a campaign (campaign-submit.html); the
     CFC accepts, returns or declines it (campaign-review.html). Accepting
     creates the campaign and the CFACC's deliverables list.
  2. Planning conference (T-35). CAOC + host JFACC work through the PCON
     checklist (product "Planning Conference", internal, never released):
     basics, people/channels, intent, forces and ATO lines, REDFOR, airspace,
     targeting, comms, SPINS inputs, mission file.
  3. In parallel after the conference:
       - Host sends the draft .miz with REDFOR laid in (T-30)   [HOST]
         on mission-file.html: versioned; the page keeps the BLUE flights
         (-> ATO line requests) and REDFOR units (-> target nomination);
         each version shows what changed. Map x/y become lat/lon only for a
         calibrated theater (Persian Gulf built in; others calibrated once
         from a Coalition Parser CSV of the same mission). Each version is
         also scrubbed for TACAN/ICLS duplicates, map TACAN clashes, ident
         problems and differences from the tanker tracks / SPINS carriers.
       - Host JFACC requests ATO lines (T-28)                    [HOST]
  4. Commander's Intent (T-26), AOD with the host JFACC (T-24).
  5. JIPTL (T-21) on the Target nomination page (targeting.html): REDFOR
     order of battle -> classify -> group -> AO, Area of Operations (box or point +
     radius on that page) -> score (key-task + tier weight) -> cap -> T10001...
  6. TDP book (T-18) on tdp.html: one target folder per JIPTL target. "Draft
     missing folders" pre-fills from the nomination data: coordinates,
     composition, DMPIs (critical unit first), threats within 20 NM (SAM/AAA,
     range and bearing), BDA requirement by category. Analyst completes each
     folder and marks it Ready; the book is approved as the TDP product.
  7. MAAP (T-16) on maap.html: packages (name, TOT, push, JIPTL targets) built
     from the ATO lines; each line sits in a column by role (strike, SEAD/
     DEAD, escort/sweep, tanker). Live checks: grade A target not covered,
     line in two packages, no TOT / target / strike / SEAD, line TOT more than
     20 min off the package TOT, open Human line, standing line (DCA/CAS/AEW)
     inside a package, one tanker feeding packages under 30 min apart.
     "Apply to ATO" writes the package letters onto the ATO (ATO -> draft).
  8. Human ATO lines committed by groups via Discord (T-10).
     ACO + theater map (T-8): built once the lines are committed, from the
     airspace agreed at the planning conference, before the ATO is final.
     ATO final (T-7).
  9. SPINS with the host JFACC (T-6).
 10. Comm Plan -- built LAST, once everything else is final (T-5). TAC ADMIN
     net carries TAC COORD and TAC ADMIN; Guard is standard and not listed;
     airfield/ATC frequencies stay out.
 11. CFACC approvals, then ONE PUBLISH on the CAOC Dashboard, NO LATER THAN
     T-72h: every approved product -> every active campaign group
     (versioned), plus three optional DKS exports (section 4.6):
       - ACO + theater map -> DKS OVERLAY (drawn on the DKS theater map for
         that mission; it does NOT go into the .miz)
       - Comm Plan -> DKS MANAGE AGENCIES (persistent theater frequencies for
         the whole campaign; normally only tankers and JTACs change)
       - SPINS Addendum A (AET tables, RAMRODs) -> DKS KNEEBOARDS
 12. HOST ONLY: builds the final .miz (T-24h), readiness, mass brief, first
     mission (T-0).
 13. HOST debrief (T+1) on debrief.html: per ATO line flown/result/remarks,
     BDA per JIPTL target (damage, re-attack), Blue losses, Red losses / new
     threats, campaign progress, Tacview link, notes. It seeds the CAOC's BDA
     rollup as a draft.
 14. CAOC "Cycle to next ATO" (Dashboard): ATO day + 1, next mission date,
     AOD/JIPTL/TDP/MAAP/ATO/BDA back to draft. Mission cycle (weekly
     missions; about 4 days from one mission to the next PUBLISH), days
     before the next mission: debrief T-6.5, BDA + AOD T-6, JIPTL T-5.5,
     TDP T-5, MAAP T-4.5, line commits T-4, ATO + tanker/JTAC frequency and
     SPINS changes T-3.5, PUBLISH T-72h, host .miz update T-24h, mission T-0.

4.1 COMM PLAN (COMM MATRIX) -> DKS COMM PAGE + "MANAGE AGENCIES"
-----------------------------------------------------------------
The Comm Plan is a campaign-long COMM MATRIX (valid for the whole campaign,
not per ATO day). It has colored columns (nets), with channels numbered top
down. A channel is named by its color and row:
    e.g. RAZOR on 290.050 is WHITE 1.

Example used in the prototype (OP IRON TRIDENT: the JCEOI standard net plan
with the campaign's callsigns; UHF primaries):
  WHITE  / TAC ADMIN:    1 TAC COORD RAZOR 290.050 | 2 TAC ADMIN 292.500 |
                         3 C2 / AWACS DARKSTAR 295.000 | 4 GCI KEYBOARD 297.500 |
                         5 HOST C2 300.000 | 6 SPARE 302.500
  BLUE   / TANKERS:      1 BOOM 1 305.000 | 2 BOOM 2 307.500 | 3 DROGUE 1 310.000 |
                         4 DROGUE 2 312.500 | 5 MPRS 315.000 | 6 SPARE 317.550
  YELLOW / TACTICAL AIR: 1 CHECK IN HOWDY 230.050 | 2 PKG COMMON 235.100 |
                         3 STRIKE ARIES 240.000 | 4 SEAD SWORD 245.050 |
                         5 DCA TAILBACK 254.750 | 6 SCAR ATHENA 255.350
  GREEN  / RESCUE:       1 CSAR / PRCC GUARDIAN 260.050 | 2 RESCORT SANDY 262.500 |
                         3 SAR PANDA 265.050 | 4 ISR GOGGLES 267.500 |
                         5 SAR-B BADGER 270.050 | 6 SPARE 272.500
  PURPLE / GROUND COORD: 1 ASOC CHAOS 320.050 | 2-4 JTAC/FAC(A) 1-3 323.400 /
                         326.700 / 330.000 | 5 CAS COORD APOLLO 333.350 | 6 SPARE
  GRAY   / SPARES:       1-6 SPARE 340.000 ... 356.700
The comm hierarchy is SPINS -> JCEOI -> Comm Plan -> special plans (CSAR comm
plan, MAAP package support, ATO control lines, OPTASKLINK JICO voice); every
page finds a channel by purpose (check-in, SEAD, AWACS / C2, PRCC, SAR ...).
Available colors: WHITE, BLUE, YELLOW, GREEN, PURPLE, RED, ORANGE, GRAY, BLACK.

Channel list (on the product and in its text export), columns in this order:
    NET | CHANNEL | CALLSIGN | ROLE | FREQ

The Comm Plan goes to DKS with PUBLISH (section 4.6):
  a) the matrix -> the DKS comm page (format still open, question 3)
  b) Manage Agencies -> populate DKS "Manage Agencies" with every
     channel as a SELECTABLE DEFAULT agency. The site previews exactly what
     would be sent:
        agency name = callsign, or "<ROLE> <CHANNEL>" when there is no callsign
                      (e.g. "BOOM BLUE 1") so names stay unique
        role, channel (e.g. "WHITE 1"), net (column title), freq
     Channels with no frequency are skipped and listed. Every channel of the
     sample has a frequency: 36 agencies.
     The send itself is disabled until the integration exists. The intent is
     to send only the released, approved Comm Plan.
Check-in / comm PROCEDURES are NOT in the Comm Plan; they live in SPINS
(section "Check-in & comm procedures"), referring to channels by matrix ID.

4.2 THEATER MAP -> DKS NAV / SPIDER / DESTINATION POINTS + OVERLAY
--------------------------------------------------------------------
Opened from the ACO ("Theater map" button). Right-click the map for an "Add"
menu, or use the point buttons. Every item has a name (set on the map in a
popup, shown on the labels, the side list and the export). "Export to DKS"
is a placeholder; "Download GeoJSON" works today.

POINT TYPES (and the DKS section each is meant for):
  NAV POINT     -> DKS Nav points            (confirmed)
  SPIDER POINT  -> DKS Spider points         (confirmed)
  DEST POINT    -> DKS Destination points    (TBC -- please confirm)
  THREAT        -> DKS Overlay               (TBC -- please confirm)
       A threat has a DCS system (e.g. "SA-10 Grumble (S-300PS)") and a range
       ring in NM (a default per system, editable). Default rings (approximate,
       please sanity-check): SA-5 130, SA-10 40, Patriot 54, SA-2 22, SA-11 19,
       SA-6 13, SA-3 13, HQ-7 8, Hawk 24, NASAMS 15, SA-15 6.5, SA-8 5.5,
       SA-19 4.3, SA-13 2.7, SA-9 2.3, Roland 4.3, Rapier 3.6, Chaparral 4.5,
       Avenger 2.3, SA-18 2.8, Stinger 2.6, ZSU-23-4 1.3, ZU-23-2 1.3,
       Gepard 2.2, S-60 3.2.
  Point fields: name, type, lat/lon (shown in DCS degrees + decimal minutes,
  e.g. N42 16.200' E042 49.200'), elevation (ft), notes.

OVERLAY SHAPES / CONTROL MEASURES (all -> DKS Overlay):
  FLOT          Friendly line drawn with semicircles (scallops) bulging toward
                the enemy; "FLOT" label at both ends; a "Flip" setting picks
                which side the enemy is on (left/right of the drawing
                direction). Field: effective DTG.
  FSCL          Solid black line; at both ends: "FSCL" with the establishing
                HQ and effective DTG below it. Fields: establishing HQ, DTG.
  MRR corridor  Line with width (NM), floor, ceiling, effective time.
  Tanker track  USAF AR anchor: LEFT-HAND racetrack, default 50 x 20 NM
                (adjustable), no centerline. Points:
                  ARCP  - anchor point at the start of the refueling leg
                          (tanker entry)
                  ARIP  - OPTIONAL; about 10 NM before the orbit ENTRY
                          (receiver entry); moves with ENTRY
                  ENTRY - orbit entry point
                  EXIT  - exit point (default 15 NM past the end of the leg)
                All four points are nameable (e.g. "ARCP TEXACO NORTH").
                Fields: length, width, refuel-leg heading (deg T), ARIP yes/no,
                floor, ceiling, tanker callsign, freq (suggests Comm Plan
                channels).
  HVAA orbit    Racetrack (width NM), floor, ceiling, asset callsign, freq.
  Artillery ROZ Polygon with floor and MAXORD (ft), firing unit, effective.
  Plain shapes  Box, circle, polygon, line -- for the overlay.
  Any shape can be linked to an ACO airspace measure by name.

GeoJSON export (FeatureCollection, [lon, lat]):
  points:   properties {name, kind:"point", pointType, dksSection, elevation,
            threatSystem, ringNM, notes}
  AR track: Polygon (racetrack outline) with properties {name,
            kind:"arTrack", length, width, heading, aripOn, altLo, altHi,
            callsign, freq, pattern:"left-hand racetrack",
            arip|arcp|entry|exit: {name, coordinates:[lon,lat]}, ...}
            (arip is null when there is no ARIP)
  others:   LineString / Polygon / Point(+radiusMeters for circles) with
            {name, kind, measureType, color, acoMeasure, dksSection:"Overlay",
            + the measure's fields, e.g. flip, hq, time, width, maxord}

4.3 ATO LINE REQUESTS -> DISCORD POST WITH COMMIT BUTTON
---------------------------------------------------------
(Full contract: docs/ATO_Discord_Integration.md in the repo.)

Flow:
  1. The campaign's Group JFACC/LNO opens "ATO requests" (ato-request.html)
     and either:
       - loads the group's .miz: the site reads it in the browser (zip ->
         "mission" Lua table), lists BLUE flights, marks player slots
         (skill Client/Player) as HUMAN and the rest as AI, pre-fills
         airframe, number of aircraft, callsign, mission (from the DCS task),
         start type; the JFACC ticks which flights to request; or
       - fills the request form: airframe, number of aircraft, mission,
         Human/AI, TOT, target (JIPTL number), package, callsign, base,
         commit-by, notes.
     Example: OP IRON TRIDENT requests a 4-ship of F-15Es, Human.
  2. AI lines go straight onto the ATO (the sponsor builds them in the .miz).
     HUMAN lines get a mission number (ATO day + 6xx, e.g. 8603), status
     OPEN, and the site emits "ato_line.open" to the bot, with recipients =
     every ACTIVE registered group whose registered airframes include that
     airframe (from the squadron/group registration info).
  3. The bot posts the line to those groups' Discord with a COMMIT button
     (custom_id "ato_commit:<line_id>").
  4. A unit presses Commit -> the bot calls the site:
        POST /api/ato-lines/{line_id}/commit
        { "group_id": "...", "discord_user_id": "...", "discord_username": "..." }
     FIRST COMMIT WINS. Responses:
        200 ok | 409 already_committed (+committedBy) | 422 airframe_mismatch |
        409 line_cancelled / line_ai | 404 unknown_line / unknown_group
  5. The site marks the line COMMITTED, makes that group the tasked unit on
     the ATO, adds the group to the campaign if needed, and emits
     "ato_line.filled" (filled_by + recipients) so the bot can edit every
     copy of the post ("Filled by <group>", Commit disabled).
  6. The Group JFACC sees "Filled by <group>" on the request page and on Op
     Status; staff see it on the dashboard's "ATO line requests" panel and on
     the ATO (unit column shows the group, OPEN, or AI).
  The JFACC can CANCEL an open line ("ato_line.cancelled") or RELEASE a
  commitment, which re-opens the line and re-emits "ato_line.open" with the
  same line_id.

"ato_line.open" payload fields:
  event, line_id, campaign_id, operation, ato_day, msn, airframe, aircraft,
  mission, crew, tot, target, package, callsign, base, notes, commit_by,
  requested_by {group_id, group, jfacc}, recipients [{group_id, group}],
  components [{type:"button", label:"Commit", style:"success",
               custom_id:"ato_commit:<line_id>"}]

.miz type -> registered airframe mapping (js/ato.js DCS_AIRFRAMES), e.g.:
  F-15ESE->F-15E, FA-18C_hornet->F/A-18C, F-16C_50->F-16C, A-10C_2->A-10C II,
  F-14B->F-14B, AV8BNA->AV-8B, M-2000C->M-2000C, AH-64D_BLK_II->AH-64D,
  UH-1H->UH-1H, KC135MPRS->KC-135 MPRS, KC-135->KC-135, E-3A->E-3A ...
  Matching ignores spaces, dashes and slashes.
DCS task -> mission: CAP/Intercept->DCA, Fighter Sweep->OCA, Escort, SEAD,
  CAS, Ground Attack/Runway Attack/Pinpoint/Antiship->Strike, Refueling->AR,
  AWACS->AEW, Reconnaissance->ISR, Transport->Airlift, AFAC->SCAR.
Sample mission: samples/iron_trident_viper.miz. The JFACC can also use the
mission file already sent on mission-file.html ("Use mission file vN").

In the prototype, the request page's "Discord post" preview has "Commit as
<group>" buttons that call the same commit logic, standing in for the bot.

4.4 GROUP PACK -> DKS
---------------------
On Op Status each group can download a "group pack" (one text file: the
group's ATO lines plus every product released to it) and the PILOT PACKAGE:
the zip of printable pages that PUBLISH posts to the group's Discord (CI,
AOD, ATO, SPINS, SPINS Addendum A, ROE, Comm Plan, ACO, OPTASKLINK, and TDPs
for INT targets). Groups make their own GRGs (grg.html, unit portal) and can
download each as GeoJSON for DKS.

4.6 CAMPAIGN PACKAGE PUBLISH -> DKS
-----------------------------------
PUBLISH (index.html, the CAOC Dashboard, due NLT T-72h) is one dialog:
approve the products saved and ready (one tick each), release to the groups,
the three DKS exports, and the Discord pilot package. Overlay is pre-ticked
on its first export or when the ACO changed; Agencies only when the Comm Plan
changed since the last export (the Dashboard lists added / changed / removed
channels; tanker and JTAC channels are marked "may change"); Kneeboard when
the SPINS were re-released or the ATO cycled since the last send. Each
export is versioned per campaign. ATOs are designated by letters (day 1 =
AA, day 8 = AH); events carry ato_day (number) and ato (letters).
Events queued (prototype: db.dksOutbox; formats to be agreed):
  overlay.update     { campaign_id, operation, ato_day, overlay_version,
                       measures: [ACO measures], points: [...],
                       shapes: [...] }   -> DKS Overlay for that mission
                                            (not written into the .miz)
  agencies.update    { agencies_version, agencies: [{ name, role, channel,
                       net, freq }], changes: [{ kind, channel, ... }] | null }
                                         -> DKS Manage Agencies
  kneeboard.update   { kneeboard_version, ato, section: "SPINS Addendum A",
                       title, spins_version, effective: "0300Z",
                       pages: [{ ato, ato_day, effective, ramrod,
                                 aet: { rows: "ABCDEFGHIJKLM",
                                        cols: "NOPQRSTUVWXYZ",
                                        cells: ["XHTS...", ...] } }],
                       html }            -> every crew's DKS kneeboard
                       (one page per ATO from the current one, a week
                       ahead; released SPINS only; html = the rendered
                       addendum, if DKS would rather show it as is)
  package.published  { package, products: [{ pid, v }] }

4.7 ATO LINE TARGET -> DKS "ASSIGN TARGET"   ** REQUIRED **
-----------------------------------------------------------
NOTE FOR THE DKS DEVELOPER: when an ATO line is matched to a JIPTL target
(the line's "Target / Area" holds a JIPTL target number, e.g. T10001, set
on the ATO or by the MAAP), that assignment must carry over to DKS and
show up in the DKS "Assign Target" function for that flight. The pilot
should open DKS and find the target already assigned to their line, not
have to pick it again.

Per assigned line the site can send:
  line:    msn, callsign, airframe, number of aircraft, mission type, TOT,
           package, tasked unit (group)
  target:  JIPTL target number, name, category, location (MGRS), desired
           effect, task, grade
  DPIs:    from the target folder imagery (folder.html, img/targets/...):
           one per vehicle -- DPI id (A001...), critical element, unit
           type, lat/lon, MGRS, elevation (ft MSL), weapon (TDP folder).
           The DMPI (the vehicles' mean point) is a reference only, never
           a targeting aimpoint.
  key task: the Commander's Intent key task the target serves (number and
           text), as printed on the ATO line (AMPN ... KEY TASK:n)
Lines whose "Target / Area" is an area (CAP, kill box, AO), not a JIPTL
number, have no target to assign.

When it is sent: with each PUBLISH (as part of package.published, or its
own event, e.g. targets.assigned { ato_day, lines: [...] }), and again
whenever an ATO change re-matches a line to a different target. Format,
event name and how DKS identifies the flight (msn, callsign, or the DKS
mission/flight id) are open -- see question 9 in section 8.

4.8 PERSONNEL RECOVERY: DKS DEBRIEF EJECTIONS -> PRCC; CSAR ROUTE -> DKS
-------------------------------------------------------------------------
(Full contract: docs/PR_DKS_Integration.md.)
  1. DKS Debrief logs each ejection and posts "pr.ejection" to the site:
     event_id, campaign_id, time_utc, takeoff_utc, pilot {callsign,
     player_name, group_id}, aircraft {type, msn}, position {lat, lon,
     alt_ft} (the seat / parachute position, not the wreck), status, chute,
     injury, cause. One event per crew member.
  2. The site's PRCC page (prcc.html) matches it to the ATO line (msn), the
     pilot's ISOPREP (player_name) and the SPINS release in force at
     takeoff_utc, and works it through report, locate & authenticate,
     support, recover, reintegrate.
  3. The PRCC builds the CSAR route from theater-map SPIDER POINTS; the site
     sends "pr.csar_route" (ordered points, the survivor as the objective,
     dks_section "Spider points") for DKS to load.
  4. The CSAR task force package ("pr.csartf_package") goes to the groups
     flying the rescue; it carries the survivor's ISOPREP answers, so it
     must reach only those groups' leads.
  Planned follow-ups from DKS: pr.position_update, pr.status (picked up,
  captured ...).

5. DATA FORMATS (FIELDS YOU WILL RECEIVE)
--------------------------------------------------------------------------------
Comm matrix (Comm Plan product content):
  matrixName, srs, matrix: { rows: N, columns: [ { title, color,
     cells: [ { role, callsign, freq }, ... one per row ] } ] }
  Channel ID = "<color> <row number>".

Theater map (per campaign): points[] and shapes[] as in section 4.2.

ATO line (per line):
  id, cid, msn, airframe, num, role, crew (Human|AI), tot, target, pkg,
  callsign, base, notes, commitBy, source (.miz name or "Request form"),
  mizGroup, requestedBy (group id), requestedByUser (JFACC), recipients[],
  status (open|committed|ai|cancelled), postedAt, committedBy,
  committedAt, committedByUser. Mission types include RESCORT and SARCAP;
  lines the PRCC requests have source "PRCC", pkg "CSAR", no requestedBy
  group and requestedByUser "<callsign> (PRCC)".

ATO mission row (on the ATO product):
  msn, pkg, group (tasked unit or ""), callsign, type, num, crew, role,
  tot, target, tanker, lineId

JIPTL row: id (T10001...), name, task (the CI key task number), taskName,
  grade (A-D), cat, loc, effect
Registered group: id, name, airframes ("F-15E" / "F-16C, F/A-18C" ...),
  contact (liaison), members, tz, status (active|pending)
